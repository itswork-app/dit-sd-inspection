# PostgreSQL Command Contract Catalogue

**Status:** PO product semantics for CMD-011–020 APPROVED; detailed engineering/security contract OPEN; NOT approved for implementation  
**Version:** 0.4.5 | **Date:** 2026-11-24  
**Decision basis:** T-14, T-15, T-16, T-17, T-18; Package L/M; canonical permission registry v0.2.2.

## 1. Purpose and boundary

This catalogue expands the 28 logical authorization families into individual command/read contracts. It is a design artifact. It does not create PostgreSQL functions, Vercel routes, migrations, grants, RLS policies or role assignments.

**Naming rule:** `CMD-001..054` are stable proposed catalogue IDs; CMD-001..048 are the original domain operations and CMD-049..054 are the NLA-001 notification extension. Command names are logical names. No physical PostgreSQL function name or REST route is approved by this document. If implementation later uses `cmd_<name>_v1`, that is a candidate naming convention only and must be checked against the actual schema/function inventory before adoption.

**Authority rule:** permission codes are taken from the canonical registry draft. They are not approved for seeding. The registry's permission/role semantics and role grant matrix remain subject to PO/security approval. Commands marked blocked are intentionally not implementable until their missing institutional authority or physical schema is resolved.

## 2. Mandatory shared execution contract

1. Vercel route validates HTTP method, content type, body size, schema version and allowlisted request fields, verifies Supabase session, and forwards the caller JWT. It never accepts actor, role, permission or effective scope as trusted input.
2. PostgreSQL derives actor from `auth.uid()`, resolves one active approved `app_users` record, and evaluates permission grant, validity interval, scope, state and SoD within the same transaction as mutation.
3. All protected browser roles have no direct INSERT/UPDATE/DELETE on business/governance tables. `CMD` in RLS catalogue means command-only mutation, not a browser DML grant.
4. Protected state-changing commands follow PO-approved T-18 Option A: narrow SECURITY DEFINER wrappers with a dedicated least-privileged NOLOGIN owner, fixed empty search_path, schema-qualified objects, strict input validation, caller-JWT actor derivation, PUBLIC/anon denial and exact-signature EXECUTE grants. SECURITY INVOKER remains preferred for scoped reads and non-elevated helpers. Approval of the model does not approve any individual function or ACL.
5. Every state-changing command appends its required domain/audit event in the same transaction. Audit failure rolls back the mutation. External Storage/PDF work uses an explicit intent/finalization or outbox/reconciliation state; never hold database locks over network or object transfer.
6. Idempotency for mutations is scoped to authenticated actor + command + resource scope + opaque key. Hash canonical schema version + semantic payload. Same hash returns the prior result after reauthorization; different hash returns `IDEMPOTENCY_KEY_REUSED`. Reads do not require write idempotency.
7. Lock only invariant-bearing rows, following the candidate resource-rank proposal in LOCK-GRAPH-001: L00 idempotency → L10 capacity when relevant → L15 principal → L16 role grants → L17 scope grants → conditional L18 authorization catalog → L20 canonical identity → L30 project/session → L40 instrument/version → L50 assignment → L55 membership → L60 unit → L70 association → L80 claim → L90 inspection → L100 dependent mutable aggregates → L110 append-only facts. This is a review hypothesis only: it is NOT approved, complete or proven acyclic. Each command locks only applicable resources; exact paths and implicit database edges remain subject to Engineering/Database/Security review. Multi-row locks use deterministic total ordering.
8. Responses use stable typed outcomes; unauthorized callers receive no resource-existence details. Server/database time is authoritative.
9. Route-level validation is defense-in-depth; PostgreSQL repeats every security-relevant validation. No generic update-any-row RPC or arbitrary SQL endpoint.
10. Every function signature, owner, security mode, search_path, caller role, EXECUTE grant, read/write set and test must be reviewed against actual deployed schema before migration.

## 4. RPC signature and route contract status

The following is the required signature shape for every mutating function, not a final SQL signature:

- Input: one typed command-specific argument set; no actor ID, role code, permission code, service credential, raw SQL, or client-selected database role.
- Context: authenticated caller JWT preserved from Vercel route; PostgreSQL derives `auth.uid()`.
- Output: one versioned typed result envelope with `command_id`, `status`, `server_time`, resource/version reference where authorized, and a stable error code for non-success.
- Function execute: exact signature grant only to the intended caller role; revoke PUBLIC and unintended roles; do not grant schema-wide or function-pattern EXECUTE.
- Read commands: use explicit read RPC/view/query path with RLS and bounded filters; never reuse a mutation RPC or bypass RLS.
- REST paths: TBD. Route path/method/version must be mapped one-to-one to the logical command in a later API contract. No path is implied here.

No SQL signature is supplied because actual schema types, composite keys, enums, Supabase role behavior and deployed function inventory have not been inspected. Inventing those would create false precision.
